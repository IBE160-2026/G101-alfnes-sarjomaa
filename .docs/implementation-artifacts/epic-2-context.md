# Epic 2 Context: Host writes Questions and Participants answer anonymously

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

A Host writes the Game's Questions, creates one personal Invite link per Participant (each shown once), follows a count-only progress figure, and replaces a lost link. A Participant opens the link on a phone with no login, answers under an honest anonymity notice, keeps an unsent draft on the device, and can return on the same device to change the Answer set until Collection closes. After this epic a real Collection runs end to end; closing it and the anonymising step belong to Epic 3. Anonymity is the product here: nothing the Host can see, and nothing the server stores or logs, may tie an Answer to an Invite link.

## Stories

- Story 2.1: Write, reorder and remove Questions while in draft
- Story 2.2: Create Invite links and open Collection
- Story 2.3: Invite link page: open, closed and unknown
- Story 2.4: Answer form and first submission
- Story 2.5: Return on the same device, change Answers, and keep unsent drafts
- Story 2.6: Collection progress on the Game page
- Story 2.7: Revoke and replace a lost Invite link

## Requirements & Constraints

- **Questions:** add, edit, reorder, remove only in *draft*; at most 20, each 1 to 200 characters; empty ones are not saved. Any change after Collection opens is refused.
- **Invite links:** created in *draft* or *collecting*; the first batch opens Collection; refused with zero Questions; at most 50 per Game, revoked ones included. Full links are shown to the Host once and never again: not after reload, not on any Host page, in any later response or in any column.
- **Answer set:** every Question shown; 1 to 5 ranked Answers per Question in separate fields (rank is field order); stored only when every Question has at least one Answer, otherwise the form names the missing Questions; empty fields ignored; an Answer is at most 80 characters. The server re-checks all of it, including more than five Answers and missing or unknown Question IDs.
- **One link, one Answer set.** The submitting device (same browser) can reopen the link, see its Answers and add, change or remove until close. Any other device or browser gets an empty form, identical to an unused link, and a submit there replaces the earlier set.
- **Host progress:** a count of submitted sets out of active links, shown as "fewer than 3" below three (never an exact number), never which links were used. No Host-visible value changes when a Participant submits, including `game.updated_at` and "Sist endret"; the Host reads no Answer before close. The product never nudges the Host to chase people: no reminders, no "who hasn't answered".
- **Revoke and replace:** while *collecting*, the Host pastes the full link; it is deleted with any Answer set and one replacement is shown once. Response and warning are identical whether or not a set existed. A revoked link behaves like a never-issued, malformed or deleted one. Refused at 50 issued links before anything changes. A pasted link that is not an active link of this Game gives an inline error, never the 404 page.
- **Anonymity in the answering flow:** no table, log or response holds a Participant's name, email, IP or device identifier. Link pages never offer or require a login and show no Host chrome, account indicator or Host link, even in a browser holding a Host session. Logs hold neither Token nor Answer text. The notice above the first Question is exact and claims no more than the product can keep.
- **Closed vs unknown:** a link of a Game not *collecting* shows the closed page, decided from the Game in the URL before any Token lookup. Malformed, unknown, revoked and deleted links show one identical unknown page. Both clear the link's `localStorage` key.
- **Quality floor:** answer form works at 360 px (also 320 px, 200 % zoom, no horizontal scroll), by keyboard and screen reader, WCAG 2.1 AA, bokmål; tests run offline without a key.
- **Conventions:** new `ErrorCode`s and bokmål messages in `src/lib/errors.ts`; every new Host action gets a foreign-ID case in `tests/integration/authz.test.ts` and every state-dependent operation a `WRONG_STATE` case in `game-state.test.ts`; every table with `game_id` cascades on delete; test titles carry FR IDs and each story adds `tests/TRACE.md` rows. Story 2.4 adds manual checklist items A2, A3, A4 (keyboard, screen reader, 360/320 px/zoom).

## Technical Decisions

- **Tables and ownership:** `question` belongs to the `questions` module; `invite_link` and `submission` to `collection`; `game` gains `invite_links_issued`, counting every link ever created. Only the owning module writes a table, and modules call only earlier ones in the order (`questions` before `collection`). `questions` exports `count` (a read) and `setReviewed` (Epic 5's only `question` write outside *draft*); `collection` uses `questions.count` to refuse link creation with zero Questions. `question.position` is dense `1..n`, renumbered in the same transaction on every remove or reorder, frozen after *draft*. All limits live only in `src/lib/limits.ts`.
- **Token and link:** `<APP_BASE_URL>/svar/<gameId>#<token>`. Token is 32 bytes from `crypto.randomBytes`, base64url (`src/lib/token.ts`); only `sha256(token)` is stored, as `invite_link.token_hash`, the primary key, unique across Games. The fragment never reaches the server. Every link creation, replacements included, goes through `games.reserveInviteLinks`, the one place that enforces the cap (`LINK_CAP_REACHED`) and bumps `invite_links_issued`. The first batch in *draft* moves the Game to *collecting* in the same transaction via `games.transition`.
- **Submission storage:** `submission`'s primary key is a foreign key to `invite_link.token_hash`, ON DELETE CASCADE, holding `answers jsonb` as `{ [questionId]: string[] }` plus `edit_secret_hash`. Validated by `src/lib/answer-set.ts` and again in `collection.submit` against stored Question IDs. A submit replaces the link's single row and secret hash.
- **Invite page shell:** the server render of `/svar/[gameId]` is generic: `<title>Toppsvar</title>`, `noindex`, no Open Graph, no Game title or Questions, `Referrer-Policy: no-referrer`, no session read, no Host chrome, and only the status unknown, closed or open, so the Token cannot reach server, host or proxy logs or `Referer`, and link previews cannot leak Questions. `/svar` has its own `not-found.tsx` for the unknown page. No auth code runs under `/svar` (the session proxy already skips it). The client reads the fragment, then gets title, Questions and any saved set only through Server Action `openInviteLink(gameId, token, editSecret?)` (token-gated reads), and submits through `submitAnswerSet`. No Token in any GET URL or query string. Unknown, revoked and never-issued links are indistinguishable to the caller.
- **Lookup and locking:** find `invite_link` by `(token_hash, game_id)` without a lock (no row means `LINK_UNKNOWN`, so another Game's Token is unknown); then `games.lockForMutation` without `hostId` and re-check the row and *collecting* under the lock, else `COLLECTION_CLOSED`. Participant calls never touch `game.updated_at`. Host revoke resolves the pasted link by `(token_hash, game_id)` inside the owned Game.
- **Edit secret and draft:** the browser generates a 32-byte secret on first submit and keeps it, with the unsent draft, under the single `localStorage` key `toppsvar:<gameId>:<first 16 chars of token>`. No hashing in the browser (`crypto.subtle` is undefined on plain `http://<LAN-IP>`); the server stores `sha256(secret)`. `openInviteLink` returns the saved set only on a matching hash; a wrong or missing secret returns exactly what an unused link returns. The key is cleared on closed or unknown. Draft saves are debounced (about 500 ms), never sent before submit, win over the server copy on load, and are cleared after a successful submit.
- **Actions and errors:** Server Actions with a sibling zod `schema.ts`, re-validated in the module entry point; result `{ ok: true, data } | { ok: false, code, message, fieldErrors? }`. New codes: `LINK_UNKNOWN`, `LINK_CAP_REACHED`, `COLLECTION_CLOSED`. Non-domain errors become `INTERNAL`; `src/server/log.ts` takes only `{ module, op, code, sqlstate }`; nothing logs a Token, hash, edit secret, Answer or `/svar` action argument.
- **Host reads:** `collection.progress(gameId)` returns active-link count, `issued` and submission count (below three only as "fewer than 3"). The Game page stays one route (`/spill/[id]`) whose panel follows state: *draft* shows the Question editor and link creation; *collecting* shows ProgressCount, the read-only Question list, "Flere lenker" and "Erstatt en tapt lenke". It refreshes with `router.refresh()` every 30 s while *collecting*.

## UX & Interaction Patterns

- **Question editor:** labelled textarea per Question, autosave on blur with inline "Lagret" or "Fikk ikke lagret. Prøv igjen.", counter from 160, "Flytt opp", "Flytt ned", "Slett" as buttons (no drag), "Legg til spørsmål" with "N av 20 spørsmål" hidden at 20.
- **Links:** a ConfirmDialog warns that Questions lock on the first batch. OnceLinkList shows monospace links with "Kopier", "Kopier alle", a select-the-link fallback on clipboard failure and "Jeg har kopiert lenkene"; leaving before that triggers the browser's leave-page warning. The panel reads "{issued} av maks 50 lenker brukt." Revoke is a pasted link plus a ConfirmDialog with fixed text, then a one-link OnceLinkList. ConfirmDialog is used only for opening Collection and revoke here.
- **ProgressCount:** "færre enn 3 av N svar mottatt", then "K av N svar mottatt", with the fixed sentence "Du ser bare antallet, aldri hvem som har svart." No progress bar, animation or live announcement, so a change cannot be timed against a message sent.
- **Answer form:** phone first, one column, no navigation or identity. Header, info Notice with the exact anonymity text, instruction line, then one fieldset per Question: "Svar 1", "Svar 2 (valgfritt)", "Legg til svar" up to five (focus to the new field), "Fjern" on fields 3 to 5 (focus to the previous one). Inputs: `maxlength="80"`, `autocomplete="off"`, `autocapitalize="sentences"`, `enterkeyhint="next"`, counter from 60. Non-sticky progress line, "Send inn svar" or "Lagre endringer", one helper line saying the draft stays on this device.
- **Validation and states:** on submit only; a danger error summary takes focus and links to each failing fieldset. Confirmation replaces the form; a same-device return shows a pre-filled form; a local draft shows "Du har endringer som ikke er sendt inn." with "Forkast endringene". Network-failure, closed and unknown pages have exact copy in the UX spec; loading text only after 300 ms.
- **Voice and a11y:** bokmål "du", no exclamation marks or emoji, errors say what happened then what to do; 44 px targets, visible focus ring, one `<h1>` per page.

## Cross-Story Dependencies

- 2.1 creates `question`, the *draft* panel and the `questions.count` read that 2.2 consumes. 2.2 needs Questions, adds `invite_link`, `invite_links_issued`, `reserveInviteLinks`, `token.ts` and OnceLinkList (reused by 2.7), and makes the Game page the *collecting* hub.
- 2.3 builds the `/svar` shell, unknown and closed pages and `openInviteLink` (Questions only); 2.4 adds the form, `submission`, `submitAnswerSet` and `answer-set.ts`; 2.5 extends `openInviteLink` with the edit secret and adds the draft, so 2.4 should already use the single `localStorage` key and replace-one-row semantics.
- 2.6 needs submissions (2.4) and the *collecting* page (2.2). 2.7 needs links (2.2), submissions to cascade (2.4), OnceLinkList and ConfirmDialog.
- Uses Epic 1: `auth.requireHost`, `games.lockForMutation` and `transition`, the state table, Button, TextField, Notice, ConfirmDialog, the action result shape, `ErrorCode`, the authz, game-state and cascade tests.
- Epic 3 builds on this: `collection.close` consumes `submission` and `invite_link`, closed links answer "closed", and Epic 3 adds the Host-session anonymity tests (`host-view.test.ts`, `host-anonymity.spec.ts`), the server-output capture and the close and race cases in `collection.test.ts`. Keep Host pages free of per-link state and Answer text so those pass.
