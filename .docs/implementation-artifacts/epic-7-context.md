# Epic 7 Context: The examiner runs it without keys: Demo mode, Judge evaluation and hand-in

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

The examiner clones the repository, starts Demo mode in three commands (`git clone`, `npm install`, `npm run demo`), sees Judge Groups produced from Stored rulings, and runs the tests and the Judge evaluation offline. Grouping quality is measured with pinned, reproducible figures instead of claimed. Every Stage 1 consequence is traced to a test or a manual check, so the group can declare the Stage 1 acceptance gate (SM-1) passed and Stage 2 can be considered. The README states the limits and cuts honestly. All of it works with no key, no paid account and no network. The pilot deployment is optional and the first thing cut.

## Requirements & Constraints

- **Dates and build order:** the Stage 1 freeze is 1 December; after it only fixes, tests and the README change, and time for them is reserved before it. The reflection report is written 2 to 4 December and the repository and report are handed in 5 December. Build order, each step leaving a runnable app: accounts and Games; Questions, links and Collection; close; Grouping, fallback and counters; Review and Board; play and a full round without a key; then Demo mode, the Judge evaluation and the hand-in checks (this epic).
- **SM-1 gate:** every testable Stage 1 consequence is covered by an automated test or, where it cannot be automated, by a manual checklist committed with the code, and the suite passes with no network. SM-1 is counted without slip-list items the README names as moved to Stage 2. A failure needs a fix or, only for a slip-list item, a stated README slip.
- **Traceability (`tests/TRACE.md`):** one heading per Stage 1 FR (1 to 21, 23 to 27, 30 to 32), each mapping its consequences to a test file or manual item, with test titles starting with the FR ID. `tests/unit/trace.test.ts` checks the headings and fails if any Stage 1 FR is missing. An "Open" bullet marks a consequence whose proof is not there yet, and an open consequence is not covered; the README consequences (FR-14 anonymity section, FR-31 and NFR-1 commands and demo login, NFR-8 environment table and zip) stay open until 7.4 closes them. `game-state.test.ts` walks every operation against every state and asserts exactly the permitted table.
- **Manual checklist (`tests/manual/checklist.md`):** A1 to A10, the NFR-5 timing items for Review and play on the sizing Game (30 Answer sets, 15 Questions), and the demo-content item, each with a recorded result and date, run once before the freeze. The fresh-clone run (7.4) is recorded there too. The checklist holds an SM-1 gate section that stays "not passed" until every row and the SM-3 audit have a recorded pass; update it whenever an item closes.
- **SM-2, as amended 2026-11-23:** the Judge's B-cubed F1 on ProtoQA's crowdsourced dev clusters should reach 0.70, reported with precision, recall, Judge calls per Question, prompt version and model ID. Before the freeze the prompt and model may be tuned, and every version and model tried is reported with the figure. At the freeze the figure is final: below 0.70 it is reported unchanged, discussed in the reflection report, Review is the safeguard, and nothing is changed to chase it. A figure below 0.70 does not fail SM-1; the evaluation test checks only that figures are produced and reproducible offline. ProtoQA is English, so the figure says nothing direct about Norwegian Answers.
- **SM-2 status:** recorded live 2026-11-23, prompt version 1, `deepseek/deepseek-v4.1-flash`: F1 0.6849 (precision 0.9809, recall 0.5261), 1.40 calls per Question, 15 of 52 Questions fell back on `INVALID_OUTPUT` (each with 40 or more distinct items). Reasoning `medium` (F1 0.6545) and `high` (0.6304) were tried and not kept, since long reasoning pushed large Questions past the 30 s timeout. Decision: report version 1 without reasoning, no further tuning. Figures move about 0.01 between recordings, so the pinned values belong to the committed rulings. The README must list every version and model tried and say that Questions with many distinct Answers fall back to one Group per Answer. The Story 7.2 spec holds the full table.
- **Judge evaluation:** the default run replays committed rulings, reads no key (not even `.env`), makes no network call, prints aggregates only (never a Question or item), and exits 0 whatever the figure. It warns when ruling versions differ from the current ones and says whether F1 reaches 0.70. `--live` needs a key, records every Question it can, and stores a failed Question as one Group per item with model `fallback: <reason>`. `--file <path>` scores a local labelled set, aggregates only. A shell-exported `OPENROUTER_API_KEY` beats the one in `.env`; the README tells developers to check for it before key scripts.
- **Data licence:** `data/protoqa/` holds only the crowdsourced dev file. `ATTRIBUTION.md` gives the CC-BY-4.0 credit, states the changes made and covers `protoqa-dev.json`. No scraped or training file is committed.
- **Demo content:** an invented demo Host and one demo Game in *collecting* with invented Norwegian Questions and Answer sets. Closing it gives Judge Groups from Stored rulings: source `replay`, zero uncovered items, no fallback, no network call. No tracked file (fixtures, rulings, tests, `prompting/`) may hold text derived from `.idea/` or name a real person.
- **SM-3 audit:** `tests/manual/anonymity-audit.md`, run by someone not involved in the last change, using Host access, the Invite-link list and a database dump taken after the Board is confirmed. Result recorded: no Answer attributable to a link or joinable across Questions.
- **Slip list (binding):** the pilot deployment with its scheduled expiry (pilot goals SM-6 and SM-7 wait with it), the CI Postgres job, live regeneration of rulings, and the local measurement on real Answers (SM-4); end-to-end breadth beyond the required specs gives way first. The README names every slip or says none slipped. Never cut the state machine, anonymity, replay demo, network-free tests or the README.
- **README (Norwegian):** what and for whom with a screenshot in `docs-assets/`; prerequisites (Node 22.13+, git, no database); the three commands and printed demo login; an environment table saying the app runs without any key; test commands (`npm test`, `npx playwright install chromium` then `npm run test:e2e`, `npm run judge:eval`); structure linking `.docs/`, `wiki/`, `prompting/`; Stage 2 omissions and every Stage 1 cut with reasons; the SM-2 figure with all versions tried; retention runs only while the app runs and the pilot database is deleted when the course ends. The local path never mentions a host.
- **README anonymity section:** nobody can see who wrote an Answer, and Answers may be sent to an external AI service for grouping. It lists eight limits: the Host reads Answers as written; a DB operator could correlate a link's hash with its Answer set before close; the write-ahead log, freed pages and provider history can hold deleted rows after close; per-Question Answer counts between close and confirmation could link Answers across Questions; Answer text goes to the model provider when live Grouping is on; pilot access logs hold IPs and times; the three-set minimum protects only against a curious Host; Answers are readable only on the submitting device. It adds the unsent draft on the Participant's device and points to the sprint change proposal of 2026-11-23.
- **Secrets and zip:** README table, `.env.example` and `env.ts` list the same variables (tested), with no key or password in any tracked file. `scripts/make-zip.sh` builds from `git archive HEAD`, so the zip has no `.env.local`, `.idea/`, `.data/` or `node_modules/`.

## Technical Decisions

- **Demo command:** `src/cli/demo.ts` through `tsx` with `tsconfig.cli.json`, no shell syntax. It recreates `.data/demo`, migrates, seeds through module functions (`auth.createHost`, `seed()` in `src/server/demo.ts`, shared with the replay test), then starts `next dev` on `PORT` with `DATABASE_URL=pglite://.data/demo`, `JUDGE_PROVIDER=replay`, `DEMO_MODE=1` and a matching `APP_BASE_URL`. Credentials are one constant in `src/lib`, printed on start and read by the login page and the Demo band. Answers added before close become their own Groups.
- **Rulings:** JSON arrays `data/rulings/demo.json` and `data/rulings/protoqa-dev.json`, each `{ kind: "partition", promptVersion, normalizeVersion, model, question, items, assignments }` over sorted distinct normalised items. Written only by `npm run judge:record` or `judge:eval -- --live` (key needed; only `.data/` or these two fixtures). Both are now live recordings; the ProtoQA file has 15 stored fallbacks. Replay matches by normalised Question and only for the current `NORMALIZE_VERSION`, and rulings are traced into the deployed bundle.
- **Evaluation:** `src/cli/judge-eval.ts` reads `data/protoqa/dev.crowdsourced.jsonl` (52 rows though the dataset README says 51). Answers the annotators left in no cluster are dropped. An item's weight is its respondent count, its gold cluster the one holding most weight, and the score one micro-average with clusters scoped per Question. `src/lib/bcubed.ts` is pure. `src/cli` reaches the Judge only through `src/server/judge` exports, never a provider.
- **Tuning limits:** `JUDGE_MODEL` is a pinned OpenRouter ID (never a `-latest` alias) with `structured_outputs` and `reasoning.mandatory` not `true`, since the request sends `effort: "none"` and a mandatory-reasoning model rejects it with a 400 (`ERROR` on every Question). `reasoning` and `max_tokens` changes do not bump `PROMPT_VERSION`; any prompt change does. After a re-recording, re-pin the figures and version strings in `judge-eval.test.ts`.
- **Config:** `DATABASE_URL`, `PORT`, `APP_BASE_URL`, `OPENROUTER_API_KEY`, `JUDGE_PROVIDER`, `JUDGE_MODEL`, `DEMO_MODE`, `REGISTRATION_CODE`, `CRON_SECRET`, read only through `src/server/env.ts`; `.env.example` keys must equal them.
- **Scripts:** README, CI and Playwright use only: `dev`, `demo`, `build`, `start`, `lint`, `format`, `format:check`, `typecheck`, `test`, `test:e2e`, `db:generate`, `db:migrate`, `judge:eval`, `judge:record`, `judge:smoke`.
- **Tests:** integration runs on fresh `pglite://:memory:` with real migrations; Vitest forces `mock`, clears the key and rejects non-localhost. Playwright runs on `next build && next start` with a temp PGlite dir and `replay`, blocking non-localhost. Only `demo.spec.ts` uses the demo Game; the dev-mode server used by the server-output check also runs `npm run demo`, so an e2e run recreates `.data/demo`.
- **CI:** `.github/workflows/ci.yml` on pull request and push to `main`, Node 22 and 26, no key, `NEXT_TELEMETRY_DISABLED=1`, README scripts only, plus a demo smoke (start `npm run demo` in the background, poll `/api/health` until 200, stop) that runs last, after the e2e run, because Next locks its dev directory. The optional second job runs `tests/integration` on a Postgres service container.
- **Pilot (amended 2026-11-23, overrides the 7.5 story text):** Vercel Hobby (Node runtime), Neon Postgres in Frankfurt on a pooled URL, production from `main` only, `db:migrate` as an explicit deploy step, daily Cron on `/api/purge` with `CRON_SECRET`, Grouping inside the 300 s limit. Registration is open (`REGISTRATION_CODE` unset). Previews are on with `DATABASE_URL=pglite:///tmp/toppsvar` and no key. The live key has a USD 0.10 credit limit; when exhausted the Judge returns `ERROR` and Questions fall back to one Group per distinct Answer. `vercel.json` pins functions to `fra1`, next to the database, since cross-continent round trips made Host actions take 3 to 6 s and broke NFR-5 (0.3 to 1.2 s in `fra1`). A whole round played in production after Epic 6 confirmed it: Grouping 3.6 s with no fallback, every play action 3 to 786 ms, Board lock 1.22 s (including its redirect), Scores matching the Counts.
- **Process:** one branch and one PR per epic; a departure from the architecture spine amends it in the same PR.

## UX & Interaction Patterns
