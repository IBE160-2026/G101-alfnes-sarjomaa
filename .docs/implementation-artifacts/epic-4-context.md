# Epic 4 Context: The Judge groups the Answers, or the fallback does

<!-- Generated from planning artifacts. Regenerate with compile-epic-context if planning docs change. -->

## Goal

After the Host closes Collection, Grouping runs once in the background. Each Question's Answers are partitioned into Groups by the Judge, or the Question falls back to one Group per distinct normalised Answer text, and the Game reaches *in review* with or without a model key. The Judge sits behind one vendor-neutral boundary with a replay provider (stored rulings), a mock (tests only) and, last, the live OpenRouter provider, so the whole flow runs offline. The Game also keeps content-free usage counters that the Host can download as a report. Increment: close leads to *in review* with Groups on replay, mock or the live model, and nothing in the epic ever stores or logs Answer content outside the `answer` table.

## Stories

- Story 4.1: Judge boundary with replay and mock providers
- Story 4.2: Grouping runs once at close, with per-Question fallback
- Story 4.3: Usage counters and the usage report
- Story 4.4: Live Judge through the OpenRouter provider, prompt and ruling recorder

## Requirements & Constraints

- **Run once, never again:** Grouping runs exactly once per Game. Reopening Review, a second `run`, or two page loads resuming at once never re-partition a Question that already has a result, and the Groups stay unchanged. Only the lease winner runs.
- **Count:** a Group's Count is the number of distinct Contributor keys in it, computed only in SQL. Two Answers from one Contributor in one Group count once.
- **Time and cost:** the sizing Game (30 Answer sets, 15 Questions, up to 5 Answers each) groups well within two minutes. Planning figures: about 15 Judge calls, about USD 0.006, at most about 90 s; the largest Game (50 links, 20 Questions) about 20 calls, about USD 0.01, at most about 120 s, inside the 300 s function limit. No pair is judged twice. Story 4.4 times one synthetic 250-item Question live and replaces the token and latency estimates in the architecture delivery notes.
- **Fallback:** with no key, no stored ruling, a Judge failure or more than 30 s on a Question, that Question gets one Group per distinct normalised text, `origin = fallback`, `fell_back = true` and a reason from `NO_KEY | NO_STORED_RULING | TIMEOUT | ERROR | REFUSAL | INVALID_OUTPUT`. Other Questions keep their Judge Groups. A missing key is a normal state, not an error: close succeeds and the Game still reaches *in review*.
- **Stored result per Question:** source, prompt version, normalize version, model ID, Judge calls, uncovered items, `fell_back` and `fallback_reason`. Every result records the prompt version and model ID of the provider used.
- **No network in tests or demo:** the Judge uses stored rulings or mocks by default, and live calls are opt-in. Vitest forces `JUDGE_PROVIDER=mock`, clears the key and rejects non-localhost requests. Playwright uses `replay`. The whole suite passes offline with no key.
- **Usage counters (content-free):** per Game, `judge_groups_proposed`, `groups_merged`, `answers_moved`, `groups_created`, `groups_renamed`, `groups_discarded`, `groups_restored`, `judge_calls`, `questions_fell_back`. This epic bumps only `judge_groups_proposed`, `judge_calls` and `questions_fell_back`; Review owns the rest. Counters hold no Answer text or identity and are deleted with the Game.
- **Usage report:** returns the counters, each Question's `source` and `fell_back`, and each Group's `origin` and `edit_count`. It contains no Answer text and no Group label. Another Host's Game gets the same response as a Game that does not exist.
- **Privacy at the Judge:** only the Question text and the distinct normalised items are ever sent. No Contributor key, rank or Answer-set information reaches a provider. The live request must route only to providers that honour the schema and do not store or train on the data.
- **Conventions:** new `ErrorCode`s carry bokmål messages in `src/lib/errors.ts`; test titles carry FR IDs; each story adds rows to `tests/TRACE.md`; new state-dependent operations get a row in `src/lib/game-state.ts` and a `WRONG_STATE` case; a foreign-Host case for the report; every new table cascades on Game delete; no Stage 2 stubs or comments (no `match` on the Judge); a departure from the architecture spine amends it in the same change.

## Technical Decisions

- **Judge boundary** (`src/server/judge/index.ts`): exports `getJudge()`, `JudgeError` (with a `reason` from the fallback list) and `Judge` with `info { provider, model, promptVersion }` and `partition({ question, items }, signal)` returning `{ assignments, calls, uncovered, source: 'live' | 'stored' }`. Nothing outside `src/server/judge` imports a provider or calls the model endpoint, enforced by an ESLint zone. The UI layer never imports a provider.
- **Output validation, in every provider:** `assignments.length === items.length` and every value an integer, otherwise `JudgeError('INVALID_OUTPUT')`. Valid output is renumbered in first-occurrence order `0..k-1`.
- **Selection:** `JUDGE_PROVIDER` picks `openrouter`, `replay` or `mock`. Unset means `openrouter` when `OPENROUTER_API_KEY` is set, otherwise `replay`. In Story 4.1 unset still means `replay`; the key-based default arrives with 4.4. Only the three AD-21 variables (`OPENROUTER_API_KEY`, `JUDGE_PROVIDER`, `JUDGE_MODEL`) are read, through `src/server/env.ts`; the fixed env-key list test fails on any addition.
- **replay provider:** loads `data/rulings/*.json` and finds rulings by `normalize(question)`. It applies stored clusters to the items a ruling covers and makes each uncovered item its own cluster after them, reporting `source: 'stored'`, `calls: 0` and the uncovered count. With nothing covered it throws `NO_KEY` when no key is configured, otherwise `NO_STORED_RULING`. Groups made only of uncovered replay items get `origin = fallback`.
- **Stored ruling format:** `{ kind: "partition", promptVersion, normalizeVersion, model, question, items, assignments }` with sorted distinct items; fixtures are JSON arrays; a malformed file fails with a clear error. `demo.json` and `protoqa-dev.json` are written only by `npm run judge:record`. 4.1 tests use invented fixtures under `tests/`. `next.config.ts` gets `outputFileTracingIncludes` for `data/rulings/**`.
- **mock provider:** deterministic, no I/O, uses a map the test supplies or one cluster per item. Used only by Vitest.
- **openrouter provider:** built-in `fetch`, no SDK, to the OpenRouter chat-completions endpoint. It uses a stored ruling only when the item set matches exactly (`source: 'stored'`, no `fetch`). Otherwise: model `JUDGE_MODEL` (default `deepseek/deepseek-v4.1-flash`, a pinned ID, never a `latest` alias), strict JSON-schema `response_format` for `{ assignments: number[] }`, `temperature: 0`, a bounded `max_tokens`, and `provider: { require_parameters: true, data_collection: "deny" }`. One retry on invalid output, 429 or 5xx, inside the signal; `calls` counts the retry. An aborted signal gives `TIMEOUT`, `finish_reason: "content_filter"` gives `REFUSAL`.
- **Prompt:** lives only in `src/server/judge/prompt.ts` with `PROMPT_VERSION`; any prompt change bumps the version; no real person's text.
- **Items and calls:** a Question's items are its distinct normalised texts (`src/lib/normalize.ts`, `NORMALIZE_VERSION`) sorted by code-unit order. One `partition` call per Question under a 30 s `AbortSignal`, at most 5 Questions at once, and the Judge is never called inside a transaction (asserted with a spy). Any non-`JudgeError` throw counts as `ERROR`.
- **Writing results:** one transaction per Question: `lockForMutation` for *grouping*, insert the Groups, set `answer.group_id`, insert one `grouping_result` (unique per `question_id`), and bump counters. A Question that already has a result is skipped. Only the `grouping` module writes `answer`, `answer_group` and `grouping_result`, through writers that take `tx` first; `games.bumpCounters(tx, gameId, delta)` is the only writer of `game_counter`.
- **Running and resuming:** the close action calls `after(() => grouping.run(gameId))`; module functions never call `after()`. A Host page load in *grouping* calls `grouping.resumeIfStale(gameId)`, which takes the lease with `acquireGroupingLease` (compare-and-set on `grouping_lease_until < now()` in database time) and runs only if it won. The runner extends the lease after each Question. Both paths end in `finishIfComplete`, which locks, counts results and moves the Game to *in review*. `grouping.progress(gameId)` returns Questions done out of total. If the Game is deleted mid-run the run stops quietly. The Game page already exports `maxDuration = 300`, and the close action inherits it.
- **Errors and logging:** `after()` tasks and entry points turn any non-`DomainError` into `INTERNAL`, with no cause or message. `src/server/log.ts` takes only `{ module, op, code, sqlstate }`. Provider responses, items and Question text never reach a log or result.
- **Report route:** `GET /api/spill/[gameId]/rapport` is a Host-authenticated Route Handler that calls `await connection()`; it is one of only three allowed Route Handlers.
- **Schema:** `answer_group` (with `origin` of judge or fallback) and `grouping_result` plus `answer.group_id` in 4.2; `game_counter` (keyed by `game_id`) in 4.3. Neither Group table nor `answer` may carry timestamps, serials, identity or time-ordered IDs. Generated migrations are committed.
- **Scripts:** `npm run judge:record` (4.4) writes rulings in the stored format, only under `.data/` unless writing the designated demo or ProtoQA ruling sources, and refuses with a clear message without a key.

## UX & Interaction Patterns

- **Grouping panel** (Game page in *grouping*): StatusBadge "Grupperer" and the text "Dommeren, en KI-modell, grupperer svarene … Det tar vanligvis under to minutter." (already in place from Epic 3; it is the only place the Judge is explained). Epic 4 adds the line "N av M spørsmål ferdig" from `grouping.progress`, with the page refreshing every 3 s. The panel is its own loading state.
- **Slow or interrupted run:** "Grupperingen tar lengre tid enn vanlig. Last inn siden på nytt." The next page load resumes after the lease. No manual grouping is offered here.
- **Judge failures are not shown in the panel.** They surface later as the fallback Notice in Review (Epic 5), which reads `fallback_reason`.
- **In review summary** on the Game page when Grouping completes: StatusBadge "Til gjennomgang", the Question count, Groups proposed and the number of fallback Questions, with primary action "Gå til gjennomgangen".
- **Usage report:** button "Last ned bruksrapport" on the Game page from *in review* onward; absent in earlier states.
- **Voice and a11y:** bokmål "du", no exclamation marks, errors say what happened and what to do, 44 px targets, visible focus, WCAG 2.1 AA; the Judge term is "dommeren" and the process "gruppering".

## Cross-Story Dependencies

- 4.1 is the base: the boundary, replay and mock. 4.2 runs Grouping on the mock (Vitest default) and creates `answer_group`, `grouping_result`, `answer.group_id`, `acquireGroupingLease`, `resumeIfStale`, `finishIfComplete`, `progress` and the panel's progress and in-review summary. 4.3 creates `game_counter` and adds the bump to the per-Question transaction 4.2 writes, then the report and button. 4.4 adds the live provider, `prompt.ts`, the key-based default in `getJudge()` and `judge:record`, and its AC4 checks that every `grouping_result` records the provider's prompt version and model ID (from the Judge's `info`).
- Builds on Epic 3: the close transaction that already inserts shuffled Answers through `grouping.insertAnswers`, the `grouping` module, `game.grouping_lease_until` (set to database `now()` + 180 s at close), the six-column `answer` table, and the Game page panel. Epic 3 left a `shortcut:` marker on the grouping panel because nothing ran Grouping; Story 4.2 makes the promise true and removes it.
- The `answer` column allow-list in `anonymity.test.ts` pins six columns on purpose. Story 4.2 adds `group_id` and must extend that list deliberately, never loosen it. Keep the anonymity tests green: Host-facing reads still never select `contributor_key` or `rank`.
- Constants live in `src/lib/limits.ts` (Judge timeout 30 s, concurrency 5, lease 180 s, poll 3 s).
- Epic 5 consumes the Groups (`origin`, `edit_count`, `fallback_reason`), `grouping_result`, the other counters via `bumpCounters`, and `clearContributorData`. The report reads `edit_count`, which Review increments; the epics do not say which story adds that column, so decide it in 4.2 or 4.3. Epic 7 consumes `data/rulings/demo.json` and `protoqa-dev.json` (recorded with `judge:record`), `judge:eval`, and the replay path for Demo mode.
